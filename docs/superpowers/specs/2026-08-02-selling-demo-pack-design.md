# Пакет «продающий показ» — дизайн

Дата: 2026-08-02. Статус: утверждён пользователем (в сессии).

## Проблема

Готовимся к первому показу владельцам стоматологий. Ожидаемые возражения
(гипотезы, показов ещё не было): «наши пациенты звонят, а не пишут»,
«дорого / не верю в окупаемость», «а если бот ошибётся с живым пациентом»,
«надо подумать» (уходят без конкретики). Решение пользователя: закрывать их
инженерными доработками, БЕЗ голосовых сообщений.

Внешний аудит (dual-agent, 02.08) проверен по коду построчно. Подтверждено:

- **Сломанное обещание.** `escalated`-ответ обещает «администратор ответит
  вам здесь» (`replies.py`, шаблон `escalated`), но канала ответа нет:
  алерт даёт админу только chat_id и выжимку без PII (`escalation.py`),
  `/release` лишь возвращает диалог боту (`worker.py`). Если пациент не
  оставил контакт — связаться с ним нельзя вообще.
- «Приду» из напоминания — пустое подтверждение, статус не сохраняется
  (`fsm.py`, ветка `attend`).
- Клиника без Google Calendar не видит записи бота вообще (только цифры
  /stats вечером); экрана «сегодня» нет.
- Обёртка мед-дисклеймера собирает новый `Reply(text, buttons)` и теряет
  `button_rows`/`menu`/`contact_request` (`fsm.py::_with_medical_disclaimer`).
  Достижимый кейс: «болит зуб, завтра в 15:00» → выбор врача идёт через
  `button_rows` (`shared_helpers.py::_ask_doctor`) → пациент получает текст
  без кнопок.
- Сообщение паузы «позвоните в клинику» не показывает телефон, хотя
  `clinic.phone` есть в модели.

Отклонено после проверки: «--check даёт [OK] пустому адресу» — осознанное
решение «подсказки, не FAIL» (комментарий в `supervisor.py`); «дисклеймер +
цена одновременно» — корректное поведение, не дефект; «предотвращённые
неявки — нарисованные деньги» — механика M2 задокументирована в `stats.py`
(строгий вариант давал ≈0 на живом трафике), метрику НЕ переворачиваем.

## Решение (состав пакета)

Шесть доработок: операционная замкнутость (1–3) + денежные аргументы (4–5)
+ полировка (6). Все — детерминированный код, LLM не участвует.

### 1. Takeover: админ отвечает пациенту через бота

Канал двусторонний, оба направления новые:

- **Входящее.** Сообщение пациента в состоянии `escalated` пересылается во
  все админ-чаты карточкой «💬 Чат {chat}: {текст}» (сейчас пациент в
  заморозке пишет в пустоту). Текст идёт как есть — админ и есть адресат.
- **Исходящее.** Админ отвечает свайп-реплаем (Telegram reply) на алерт
  эскалации ИЛИ на карточку 💬. Бот шлёт пациенту «👤 Администратор:
  {текст}» (префикс на языке пациента), админу — подтверждение
  «✅ Доставлено» реплаем. Пациент остаётся в `escalated` до `/release`.

Связь «сообщение в админ-чате → пациент» держит таблица-якорь
`admin_relay(clinic_id, admin_chat_id, message_id, patient_chat_id,
created_at)`, UNIQUE(admin_chat_id, message_id), RLS FORCE. Запись
создаётся при отправке алерта эскалации, карточки 💬 и алерта плохой
оценки (фича 5). Парсинг chat_id из текста алерта отвергнут: шаблоны
двуязычные и меняются.

Края: свайп на сообщение без якоря → подсказка «отвечать нужно реплаем на
алерт»; не-текст от админа (фото/войс) → «пока только текст»; сбой
доставки пациенту → админу честная ошибка, не тишина. Якоря старше 7 дней
чистит retention.

### 2. Лента записей + «Сегодня» + утренняя сводка

- **Лента.** Подтверждённая запись / отмена / перенос → карточка во все
  админ-чаты в момент события: «✅ Запись: {имя}, {услуга}, {дата время},
  {врач}», пометка 🌙 у ночных. Шлёт узкий notifier из тех же слоёв, где
  живут эскалации (диалог, напоминания, календарный синк — вытеснение).
  Рубильника в v1 нет (пилотный масштаб); заметка в PILOT_HARDENING.
- **/today** (+ кнопка «📅 Сегодня» в консоли): записи дня по времени —
  время, имя, телефон (расшифровка на лету), услуга, врач, статус
  подтверждения из фичи 3 (✅ подтвердил / ⏳ молчит). Язык — админ-чата.
- **Утренняя сводка** в 08:30 локали клиники по паттерну вечернего
  дайджеста: список дня + «⚠️ не ответили на напоминание: N — стоит
  позвонить». Поле `clinic.last_morning_digest_date` (миграция).

### 3. Статусы подтверждения визита

Миграция: `appointment.confirm_status text NULL ('confirmed')` +
`confirmed_at timestamptz`. Кнопка «Приду» (`attend:<uuid>`, субъект уже в
кнопке) вместо пустого ответа пишет статус — с проверкой принадлежности
записи чату (вторая половина инварианта кнопок). «Отменить» уже даёт
cancel c actor='reminder' — не трогаем. «Молчит» не хранится, вычисляется:
напоминание `sent`, статус NULL. Потребители: /today, утренняя сводка.

### 4. Recall — возврат пациентов

- Миграция: `service.recall_months int NULL` (NULL = выключен) + таблица
  `recall_outreach(clinic_id, appointment_id UNIQUE, tg_chat_id, sent_at,
  status 'sent'|'booked')`, RLS FORCE. Одна отправка на приём.
- Reconciliation в цикле напоминаний: booked-приём закончился ≥ N месяцев
  назад, услуга с `recall_months`, у пациента НЕТ будущей записи, пациент
  не анонимизирован (/forget = не беспокоить) → в дневное окно клиники
  (09–21 локали) уходит «Полгода после чистки — пора на осмотр.
  Записать?». Язык — `appointment.lang`, чат — `appointment.tg_chat_id`
  (оба уже в схеме, новых PII-колонок нет).
- Кнопка `rcl:<uuid исходного приёма>` — сырая (RAW_CALLBACK_PREFIXES),
  ≤64 байта: стартует booking flow с услугой приёма; при confirm новой
  записи `recall_outreach.status='booked'` — конверсия точная.
- Консоль: в карточке услуги кнопки интервала «повторный визит: 3/6/12
  мес / выкл».
- /stats и дайджест: «🔁 recall: отправлено N, вернулось M (+сумма)».

### 5. Отзывы: перехват негатива, сбор хороших

- Миграция: таблица `review(clinic_id, appointment_id UNIQUE, tg_chat_id,
  rating int NULL, requested_at, rated_at)`, RLS FORCE +
  `clinic.review_url text NULL` (onboard `--review-url`).
- Reconciliation: приём закончился ≥2 ч назад (окно 09–21, не старьё —
  только сегодняшние/вчерашние), отзыв не запрашивался → «Как всё прошло?»
  с кнопками `rate:<uuid>:1..5` (сырые, субъект в кнопке).
- Тап: 4–5 → благодарность + `review_url`, если задан; 1–3 → благодарность
  пациенту + алерт админ-чатам «⭐{n} от чата {chat}: {услуга}, {дата}»
  БЕЗ заморозки пациента; алерт получает якорь admin_relay — свайп-ответ
  фичи 1 сразу работает. После тапа кнопки гаснут (edit), оценка одна на
  приём (повторный тап → toast «уже учтено»).
- /stats: «⭐ средняя оценка: X.X (N оценок)».

### 6. Полировка

- `bot_paused` подставляет телефон клиники, если задан (второй шаблон
  `bot_paused_phone`; пустой `clinic.phone` — текущий текст).
- Фикс обёртки дисклеймера: `replace(reply, text=…)` — сохраняет ВСЕ поля
  Reply; тест на достижимый кейс с `button_rows`.
- DEMO.md — три акта (финальный шаг, когда фичи готовы): ночная запись →
  спасённый слот (отмена из напоминания + пуш листа ожидания) → живой
  takeover (просьба человека → свайп-ответ → /release). Остальное — резерв
  на вопросы.

## Сквозные инварианты

- Новые кнопки — только сырые, несут субъект (uuid), ≤64 байта, префиксы в
  `RAW_CALLBACK_PREFIXES`; проверка принадлежности чату на месте.
- Фоновые рассылки (recall, отзывы, сводки) НЕ переписывают `conversation`
  пациента — всё нужное в кнопке (правило фона).
- Новые таблицы (`admin_relay`, `recall_outreach`, `review`) — арендные,
  RLS FORCE, в retention-карту; PRIVACY.md дополняется. Шифрованных
  колонок не добавляем (`rotate_key.ENCRYPTED_COLUMNS` не меняется).
- Новые пациентские строки — в TEMPLATES ru/uz и в пакет вычитки
  UZ_STRINGS.md (тест пакета поймает пропуск); админские — в admin_texts.
- Verification-first: тест до реализации, каждый тест проверяется откатом
  фикса. Конкурентные пути (reconciliation-циклы) — серия прогонов сьюта.

## Порядок реализации

Фиксы п. 6 (дисклеймер + телефон паузы) → 1 → 2 → 3 → 4 → 5 → DEMO.md.
Каждая фича — свой коммит + Codex-ревью. Миграции — по фиче, не одной
пачкой.

## Вне скоупа (решено)

- Голосовые сообщения — решение пользователя.
- Ручная запись пациента админом («позвонил по телефону») — не в этом
  пакете; клиника с GCal уже имеет путь через ручное событие.
- Переворот M2-метрики «предотвращено неявок» и ROI-воронка — метрика
  остаётся как есть.
- Рубильник ленты записей — по сигналу с пилота (PILOT_HARDENING).
- Пилот Ф2, показ, деплой — строго по явной команде.
