# Спека: self-service инкремент 2 — врачи, услуги, расписание, выходные

Дата: 2026-06-14. Статус: одобрено пользователем (брейншторм).
Направление — SELF-SERVICE ИЗ TELEGRAM: владелец держит клинику сам,
без CLI и без захода на сервер. Инкремент 1 (каркас консоли + цены +
FAQ + /stats + пауза кнопками) закрыт коммитом 7ec771f. Этот инкремент
достраивает: **врачи (CRUD), услуги (CRUD), расписание врача кнопками,
выходные в меню**.

Решение пользователя по объёму: **всё сразу** в одном инкременте (три
области). Каждая область проектируется изолированно — при написании
плана разбивается на под-инкременты.

## Поверхность

Админ-консоль владельца — `telegram/admin_console.py` (`AdminConsole`),
живёт в админ-чате (`clinic.tg_admin_chat_ids`): воркер перехватывает
сообщения чата ДО пациентского диалога и показывает кнопочную консоль.
Пациентский диалог из админ-чата недоступен; тест записи — со второго
аккаунта. Язык консоли — только русский (конвенция инкремента 1).

Расширяю существующий `AdminConsole` (не новый класс): те же паттерны —
reply-меню верхнего уровня (точный матч label'ов до NLU), inline-разделы,
сырой префикс `adm:` мимо tg_actions-map, pending-ввод в
`conversation.context.extras` (`adm_pending`), `fsm_state` остаётся idle.
Слэш-команды (`/dayoff`, `/dayopen`, `/pause`, …) остаются аварийным
выходом — кнопки их дополняют, не заменяют.

Мутации проходят через `onboard.py`-функции: переиспускаю
`add_doctor`/`add_service`/`set_doctor_schedule`/`set_service_price`,
добавляю `set_service_duration`, `rename_doctor`, `set_doctor_buffer`,
`activate_doctor`/`deactivate_doctor`, `activate_service`/`deactivate_service`,
`delete_doctor`/`delete_service` (последние — только для никогда не
использованных, без FK-ссылок).

## Жизненный цикл врача/услуги: деактивация (is_active)

FK `appointment.doctor_id`/`service_id` и `waitlist.service_id` —
`REFERENCES … ` без `ON DELETE` (= RESTRICT): врача/услугу с любой
записью физически удалить нельзя. Поэтому «удалить» на практике =
**деактивировать**.

Миграция **0021** `doctor_service_active`:

```sql
ALTER TABLE doctor  ADD COLUMN is_active boolean NOT NULL DEFAULT true;
ALTER TABLE service ADD COLUMN is_active boolean NOT NULL DEFAULT true;
```

Бэкфилл не нужен (`DEFAULT true` накрывает существующие строки). RLS на
обеих таблицах уже стоит. `down` дропает обе колонки.

- Деактивация → `is_active=false`: скрыт из записи/слотов, прошлые и
  будущие записи и /stats целы, можно реактивировать.
- «🗑 Удалить совсем» доступно только при нуле FK-ссылок (например,
  ошибочно добавленный врач/услуга) — `delete_doctor`/`delete_service`.
- «Врач уволился» = деактивация: история не стирается.

## Контракт is_active (центральный, в слое данных)

Фильтр ставится ВНУТРИ репозиториев (конвенция «в fsm нет сырого SQL»),
по умолчанию — только активные. Консоль получает явные `*_all`-варианты,
чтобы видеть деактивированных.

| Функция | Сейчас | После |
|---|---|---|
| `doctors_repo.doctor_list` | все | `WHERE is_active` (запись/слоты) |
| `doctors_repo.working_intervals` | все | `WHERE is_active` (open_bounds, «закрыто сейчас») |
| `services_repo.service_keys` | все | `WHERE is_active` (кнопки услуг) |
| `services_repo.find_service` / `service_id` | все | `WHERE is_active` (резолв услуги→id) |
| `services_repo.price_list` | все | `WHERE is_active` (FAQ-цены пациенту) |
| `services_repo.service_price` | все | `WHERE is_active` |
| `doctors_repo.doctor_list_all` / `service_list_all` (новые) | — | без фильтра (только для консоли) |

Сырые `SELECT … FROM doctor` вне репозиториев — добавить `WHERE is_active`
для консистентности: `stats.py` (метрика «вне рабочих часов»),
`supervisor.py --check` (счётчики активных врачей/услуг).

**Альтернатива (отвергнута):** фильтровать в каждом вызове fsm/
shared_helpers — рассыпает условие по коду, легко забыть точку →
деактивированный врач продолжит получать записи.

**Край (не трогаем):** деактивация врача с привязанным GCal — синк-петля
ходит по `gcal_calendar_id IS NOT NULL`, не по `is_active`; существующие
записи продолжают синхиться (корректно), новые слоты не предлагаются.

## Меню верхнего уровня (рестрактур)

«Цены» сливается в раздел **«Услуги»** — цена становится одним из полей
услуги рядом с длительностью и активностью. Отдельная кнопка «💰 Цены»
исчезает (убираем дубль входа к одной сущности).

```
  [ 💊 Услуги ]   [ 👨‍⚕️ Врачи ]
  [ 🏥 О клинике ] [ 📅 Выходные ]
  [ 📊 Статистика ]
  [ ⏸ Пауза ]   (↔ ▶️ Возобновить)
```

- `BTN_PRICES "💰 Цены"` → `BTN_SERVICES "💊 Услуги"` (константа + матч).
- Новые: `BTN_DOCTORS "👨‍⚕️ Врачи"`, `BTN_DAYOFF "📅 Выходные"`.
- `🏥 О клинике`, `📊 Статистика`, пауза — без изменений.
- Существующие тесты на `BTN_PRICES`/`_prices_menu` обновляются под
  новый раздел (в скоупе).

## Раздел «Врачи»

`👨‍⚕️ Врачи` → список (активные + ⚪ деактивированные) + «➕ Добавить врача».

```
👨‍⚕️ Врачи
  [ Akmal aka · Пн–Сб 09–18 ]
  [ Dilnoza opa · Пн–Пт 10–19 ]
  [ ⚪ Botir aka (скрыт) ]
  [ ➕ Добавить врача ]
  [ ◀ Меню ]
```

Карточка врача:
```
👨‍⚕️ Akmal aka
График: Пн–Сб 09:00–13:00, 14:00–18:00
Буфер: 10 мин · Календарь: привязан
  [ ✏️ Имя ]      [ 🕐 График ]
  [ ⏱ Буфер ]    [ ⛔ Деактивировать ]
  [ ◀ Назад ]
```

- **Имя** — pending-ввод текста, AES-шифрование (`rename_doctor`).
- **График** — поток ниже (шаблоны + «Свой график»).
- **Буфер** — pending-ввод числа минут (`set_doctor_buffer`).
- **Деактивировать/Активировать** — `is_active` + подтверждение. У
  деактивированного без FK-ссылок появляется «🗑 Удалить совсем».
- **Добавить врача** → имя (текст) → график (шаблон/свой) → буфер
  (или дефолт 10) → создан. Календарь из Telegram не привязывается
  (см. «Границы»); карточка показывает статус и текстовую подсказку.

### Расписание (поток «🕐 График»): шаблоны + текст смен

Решение пользователя по UX-развилке: **шаблоны + текстовый ввод смен**
(не кнопочный конструктор-грид: график ставится редко, печать «9-18»
быстрее тапов, строгий валидатор уже есть).

```
🕐 График: Akmal aka
Сейчас: Пн–Сб 09–13, 14–18
── Шаблон ──
  [ Пн–Пт 09:00–18:00 ]
  [ Пн–Сб 09–13 / 14–18 ]
  [ Пн–Пт 10:00–19:00 ]
  [ ✏️ Свой график ]
  [ ◀ Назад ]
```

- Шаблон одной кнопкой → `set_doctor_schedule` готовым словарём.
- «Свой график» → выбор дней галочками (toggle `adm:sch:day:mon` …) →
  «Далее» → pending-ввод смен текстом `09:00-13:00, 14:00-18:00` →
  строгий парсер (переиспускаю `onboard._validate_intervals`/
  `_parse_hhmm`) → один набор смен применяется ко ВСЕМ выбранным дням,
  остальные дни = выходной → `set_doctor_schedule`.
- Промежуточное состояние выбора дней — в `conversation.extras`
  (`adm_sch_days`), как `adm_pending`: переживает рестарт, чистится по
  выходе/применению.
- Кривой текст смен → повтор шага с подсказкой, без краша.

**YAGNI-отсечка:** разные часы по разным дням в одном проходе НЕ
делаются (редкий случай; добивается повторным проходом по подмножеству
дней).

## Раздел «Услуги»

`💊 Услуги` → список добавленных услуг (активные + ⚪ деактивированные)
+ «➕ Добавить услугу».

```
💊 Услуги
  [ 🦷 Чистка · 30 мин · 350 000 ]
  [ 🦷 Пломба · 60 мин · 400 000 ]
  [ ⚪ Брекеты (скрыта) ]
  [ ➕ Добавить услугу ]
  [ ◀ Меню ]
```

Карточка услуги:
```
🦷 Чистка
Длительность: 30 мин · Цена: 350 000 сум
  [ 💰 Цена ]   [ ⏱ Длительность ]
  [ ⛔ Деактивировать ]
  [ ◀ Назад ]
```

- **Цена** — существующий поток (`set_service_price`, pending-число).
- **Длительность** — pending-ввод минут (`set_service_duration`,
  новая). Валидация 5–480 мин.
- **Деактивировать/Активировать** — `is_active`. «🗑 Удалить совсем» —
  только при нуле FK-ссылок (appointment + waitlist).

**Добавить услугу — только из каталога `SERVICE_KEYS`** (9 ключей: NLU
умеет ссылаться только на них). «➕ Добавить» показывает кнопками
канонические услуги, которых ещё нет в клинике → тап → pending-ввод
длительности → (опц.) цены → `add_service`. Произвольное название
ввести нельзя.

**Альтернатива (отвергнута):** свободный ввод названия услуги — ломает
контракт «услуга = ключ из `SERVICE_KEYS`», NLU «слепнет» на услугу.

**Край (в скоупе):** деактивация услуги с активным листом ожидания
(`waitlist.service_id`) гасит активные waitlist-записи по ней
(`status='cancelled'`) — иначе матчер шлёт слоты по снятой услуге.

## Раздел «Выходные»

Кнопочная обёртка над готовым механизмом (`holiday`-таблица,
`_parse_ddmm`, валидация уже в воркере).

```
📅 Выходные
Ближайшие закрытые дни:
  [ 19.06.2026 (Курбан-байрам) ✖ ]
  [ 24.06.2026 ✖ ]
  [ ➕ Закрыть день ]
  [ ◀ Меню ]
```

- Тап на закрытый день → подтверждение → `/dayopen`-логика (снова
  рабочий).
- «➕ Закрыть день» → pending-ввод `ДД.ММ [причина]` → `_parse_ddmm` +
  вставка в `holiday` → подтверждение.
- Список — `holiday WHERE date >= today ORDER BY date` (рендер из
  `_dayoff_usage` переносится в консоль).
- Ввод даты — текстом `ДД.ММ`, не датапикером (консистентность с
  расписанием; `_parse_ddmm` отлажен; пациентский месячный датапикер
  со слотами в админку тащить избыточно).

## Верификация

Одна команда (`[OK]`/`[FAIL]`, exit-code): драйвер на фейковой сессии —
деактивирует врача и проверяет исчезновение из `doctor_list` и слотов;
правит график через консоль и проверяет `working_intervals`;
добавляет/удаляет услугу. Плюс `python -m navbat --check` (счётчики
активных) и полный `pytest` (серия 5×).

## Границы (вне скоупа, явно)

- **Привязка GCal из Telegram — НЕТ** (OAuth требует браузера). Новый
  врач создаётся без календаря; привязка остаётся `python -m
  navbat.onboard --doctor … --calendar …` + `python -m
  navbat.calendar.auth`. Консоль показывает статус календаря и
  текстовую подсказку, OAuth не выполняет.
- **Язык консоли — только русский.**
- **Разные часы по дням в «Своём графике» — нет** (YAGNI).
- **Произвольные услуги — нет** (только каталог `SERVICE_KEYS`).
- **Гранулярность прав** — любой админ-чат мутирует (текущая модель
  доверия).
